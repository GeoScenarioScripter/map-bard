# MapBard — Architecture and Build Direction

Updated 2026-10-17. This replaces the original Phase A working brief. It defines
architectural direction and constraints, **not an implementation schedule**.
Session 09's [stage roadmap](implementation-stages.md) and
[Stage 1 plan](stage-1-plan.md) supply the sequence and first-stage detail;
implementation is not started. Read [mapbard-plan.md](mapbard-plan.md)
for the product/research story, [refinement-roadmap.md](refinement-roadmap.md) for
planning inputs, and [BUILD_LOG.md](BUILD_LOG.md) for actual status.
The preceding brief is preserved in [the archive](archive/2026-10-17/mapbard-build-guide.md).

Legacy source comments citing numbered sections of the original guide refer to
that archived edition. This revision does not change the runtime API or rewrite
those implementation comments.

## 1. Principles retained and revised

1. **One semantic center, explicit artifact boundaries.** Keep `GeoNarrative`
   central; separate project metadata, analysis/evidence artifacts, and compiled
   render specifications instead of forcing everything into one object.
2. **Agent-independent execution.** The engine must inspect, analyze, validate,
   compile, preview, test, and export without a required model call or account.
   External agents and humans can supply project changes. Built-in planners are optional.
3. **Structured authoring, deterministic execution.** Agent-generated story content
   passes through versioned schemas and semantic checks. Rendering is generated by
   tested code. Custom code belongs to explicit extension boundaries, not narration.
4. **Evidence before assertion.** Compute findings with tools, preserve provenance,
   and distinguish supported observations from interpretation or missing evidence.
5. **Precise, reviewable edits.** Preserve IDs, author locks, and unrelated content;
   invalidate dependent results instead of silently keeping stale facts.
6. **Realized capabilities.** Every accepted technique must compile to supported
   runtime behavior or return a diagnostic. Schema validity alone is insufficient.
7. **One project across interfaces.** CLI, SDK, agent toolkit, and visual workbench
   use the same operations and editable state.
8. **Small complete slices.** Keep a working example through migrations. Avoid a
   schema redesign or framework buildout disconnected from a demonstrated story.
9. **Local operation and portable output.** Keep operations light and filesystem
   based until a concrete need warrants more infrastructure.
10. **Evaluation is part of delivery.** Capture checks, diagnostics, revisions, and
    reproducible outputs from the first slice.

## 2. What exists today

The 2026-10-17 baseline is the old M0–M4 implementation, not the target below.

| Package     | Existing responsibility                                                   | Likely evolution to plan                                                 |
| ----------- | ------------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| `schema`    | Zod GeoNarrative v0.1.0, inferred types, reference checks                 | Versioned project/semantic/evidence/render contracts and migration       |
| `core`      | Local vector ingestion, media registration, profiling, DashScope planning | Model-independent operations, analysis, dependencies, design compilation |
| `knowledge` | Scaffold                                                                  | Technique rules, prerequisites, explanations, scene recipes              |
| `renderer`  | Pure generation, bundle writer, plain-JS MapLibre/scrollama player        | Resolved-spec playback, TypeScript modules, testable scene runtime       |
| `cli`       | Scaffold                                                                  | Human-readable and structured interfaces over engine operations          |

Package boundaries are provisional. Define logical responsibilities before adding
new packages. Depend inward toward contracts; never put agent-host or Studio
dependencies in `schema`.

## 3. Target artifact boundaries

Names and fields below are conceptual; exact APIs belong to implementation planning.

| Artifact                      | Contains                                                                                                   | Must not be confused with                       |
| ----------------------------- | ---------------------------------------------------------------------------------------------------------- | ----------------------------------------------- |
| Editable project              | Version, resources, narrative, analysis definitions, media, design intent, extension/dependency references | Generated website or private editor state       |
| Resource/analysis artifact    | Source identity, transforms, parameters, selected records, computed findings, units and provenance         | Five-value attribute samples                    |
| GeoNarrative                  | Scenes, content/discourse, evidence-linked claims, attention targets, media, interaction intent            | Provider prompts or low-level map runtime state |
| Compiled render specification | Resolved data, scale domains, class breaks, legends, annotations, camera states, control bindings          | Unchecked agent proposals                       |
| Diagnostics/change results    | Findings tied to paths/IDs, severity, proposed remedy, affected dependencies, edit summary                 | A claim that the entire story is true           |
| Publication                   | Runtime and prepared data/assets for the selected export target                                            | The editable project                            |

Preserve supplied data identity and transformations. Source fingerprints and
engine/extension versions should allow stale output detection and reproducibility.
A dependency record supports invalidation; it need not become a distributed service
or a general-purpose knowledge graph.

The current v0.1.0 fields and inferred types remain the source of truth for
existing APIs until a tested migration changes them. Do not document hypothetical
fields as if they are already exported.

## 4. Analysis and evidence

Plan a bounded operation vocabulary: select/filter, group/aggregate, rank,
normalize with a declared denominator, spatial relation/join, and comparison of
compatible observations. Introduce only the subset needed by the chosen fixture.

Each result needs source references, operation parameters, units, relevant
coverage, and reproducible outputs. Evidence should identify the records or
aggregations supporting a factual claim. Context from text needs a source reference;
photos and video are registered media, not invented observations.

Improve profiling beyond number→ratio: units, nulls, identifiers, categories,
measurement semantics, distributions where needed, CRS, and author overrides.
Do not compute exact classifications from truncated samples. Distance/area and
temporal comparisons require an explicit method and compatibility assumptions.

DuckDB Spatial is a candidate to evaluate, not a selected dependency. Avoid
unrestricted generated-code execution in the initial operation interface. Any
later extension execution needs an explicit trust model.

## 5. Planning and design compilation

External coding agents may propose both narrative and design intent. The engine
owns execution and validation, not the author's creative choices. Preserve an
optional adapter path for the existing DashScope planner without making it a
requirement for validation, preview, or export.

Design rules should include input requirements, suitable geometry/measurement,
alternatives, reasons, and runtime support. A ratio field alone does not justify
a choropleth; examine denominator, spatial units, and task.

Compile supported intent into resolved layers, shared comparison scales,
classification breaks, legends, annotations, camera targets, transitions, and
controls. Unsupported requests must be diagnosed explicitly. Do not accept a
categorical polygon request and silently draw numeric circles.

Begin with a small scene vocabulary: establish context, reveal a pattern,
compare, follow a progression, explain an exception, and synthesize. Coordinate
media and limited linked charts when they serve the explanation. Preserve
optional content dimensions and linear sequence before branching authoring.

## 6. Runtime and export

Move the runtime toward tested TypeScript modules and a bundled browser artifact;
determinism does not require copying handwritten JavaScript verbatim. Preserve
the separation of pure generation/compilation from filesystem writes.

Playback consumes the compiled specification. Scene activation, annotations,
legends, and control behavior should be testable independently. Check mobile
layout, keyboard access, text alternatives, contrast, and reduced motion.

Distinguish presentation controls (for example opacity) from semantic controls
that change the selected time, population, or geography. Semantic changes must
recompute linked facts/annotations, mark them stale, or enter a clearly identified
exploration state. Provide a return to the authored narrative.

Maintain a portable small-story target opening from `file://` with local assets.
An optimized static-host target can support larger data and optional tiles later.
Each target declares capabilities and external dependencies. PMTiles is not
implemented today and should not be promised before its delivery/access strategy
is verified. URL media remains remote.

Plan safe asset resolution: distinguish source paths from bundle paths, contain
writes within the destination, handle collisions, resolve poster references, and
report missing files. Keep source credits and resource privacy explicit.

## 7. Engine interfaces and the agent toolkit

Build reusable operations and CLI/SDK access before host-specific wrappers.
Exact command names and flags are not settled and no public CLI currently exists.

Agents need capability/schema discovery, resource inspection, analysis execution,
project validation, scoped editing, compilation, scene preview, test/check runs,
and export. Return both useful human output and stable structured results:
operation status, artifact references, relevant IDs/paths, diagnostics, and
affected dependencies. Establish exit semantics and bounded output sizes in planning.

A diagnostic should identify a problem and a repair direction, for example:
“Comparison scenes use different color domains; use a shared domain or explicitly
explain the difference.” Include machine-readable identifiers alongside prose.

The toolkit should combine:

- A short workflow skill with linked reference material.
- Valid projects and examples of targeted changes.
- Capability and schema discovery rather than a giant static prompt.
- Instructions for investigate → author → preview → inspect → repair → verify.
- Limits on retries, explicit unresolved issues, and preservation of author work.
- Small agent-task evaluations across creation, revision, and error recovery.

Start with one coding-agent integration, such as Codex, while keeping knowledge
portable. A plugin may package the skill and tools. Add MCP if it improves access;
it should wrap the same engine operations, not duplicate their implementation.
Host-specific packaging and provider support must not become engine prerequisites.

### Built-in agent: one LLM with a purpose-built harness

The in-product agent uses one LLM, a stable system prompt, dynamically loaded
skills, and a MapBard-owned harness that maintains its loop. Do not introduce
LangGraph or a comparable graph-based agent orchestration framework. Do not model
the workflow as a fixed collection of specialized planner/designer/critic agents.
This does not prohibit ordinary provider SDKs or focused utility libraries.

Separate these responsibilities:

| Part            | Responsibility                                                                                                                       |
| --------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| System prompt   | Enduring role, operating rules, project conventions, and tool/skill discovery instructions                                           |
| Skills          | On-demand geographic methods, authoring/design guidance, and task workflows; shared with external-agent integrations where practical |
| Agent harness   | Context and session state, model turns, skill loading, tool dispatch/results, bounded iteration, user interruption, and completion   |
| Engine          | Typed analysis, validation, compilation, project edits, preview/checks, and export, independent of the agent's reasoning loop        |
| Browser runtime | Playback of the compiled publication; no authoring agent is required for readers                                                     |

Conceptual loop: assemble current context → call the LLM → resolve requested skill
or tool actions → validate and execute → return observations → continue, wait for
user input, or finish. The agent adapts its actions to results; it is not forced
through a hardcoded sequence of agent roles. Existing Plan/Design/Build concepts
remain operations and artifact boundaries rather than orchestration nodes.

Keep skill discovery lightweight: expose names/descriptions initially, load
instructions and referenced resources when needed, and record which versions
were used. A skill is guidance, not another autonomous agent or a new permission
grant. Treat input datasets, documents, and tool results as task data; distinguish
them from trusted operating instructions.

Plan the minimum harness needed for the chosen slice: explicit completion and
waiting states, tool/model errors, cancellation, retry/turn/token budgets, and
session checkpoints sufficient to resume without repeating completed mutations.
Project changes still pass through validation, revision/conflict rules, and author
locks. Record observable actions and outcomes; do not require hidden model
reasoning to be stored or exposed. Test the loop with scripted model/tool responses
before relying on live-provider evaluations.

No such harness is implemented today. The current DashScope adapter and constrained
Plan call may be reused or refactored; they are not the target runtime. The
[Stage 6 outline](implementation-stages.md) bounds the first harness; exact skill
packaging, context management, persistence, provider tool-call support and UI
integration will be detailed after Stage 5 closes. Keep the
harness separate from the engine so external agents use their own loops over the
same operations, without nesting or depending on MapBard's agent.

## 8. Shared editing and local workbench

The local workbench is a complementary view over the same project: outline,
preview, evidence/design inspector, direct camera/style edits, and change review.
It can run in a browser against a local process; framework and packaging remain open.

Plan stable IDs, scoped operations, base-revision checks, author locks, undo, and
dependency invalidation. Agent writes and visual edits must not silently overwrite
each other. Specify conflict behavior and preserve unknown extension data.

Generated HTML/JS is not the editable source. Arbitrary output edits cannot be
guaranteed to round-trip. Custom themes/components should declare editable
parameters and capabilities; missing extensions need actionable diagnostics.

## 9. Validation, repair, and research instrumentation

Separate checks into structure/references, source/evidence consistency,
cartographic semantics, runtime behavior, and presentation/accessibility.
Record what passed, failed, was skipped, or needs human judgment.

Default engine checks should be model-free and reproducible. Browser checks
exercise actual controls and scene changes. Optional screenshot critique can
suggest fixes but must not certify factual or cartographic correctness.
Repairs should address diagnostics locally and stop after a bounded budget.

Record inputs, relevant versions, operation results, diagnostics, edits, and
verification artifacts without logging secrets or private data unnecessarily.
The evaluation design in [mapbard-plan.md](mapbard-plan.md) governs research claims.

## 10. Migration and scope

Retain TypeScript strict ESM, Zod, pnpm, colocated tests, and inward dependencies.
MapLibre/scrollama remain the current renderer foundation; replacing them requires
a demonstrated need. New infrastructure and package splits are decisions to make,
not automatic consequences of this document.

Plan compatibility for the handwritten example and v0.1.0 projects before changing
contracts. Use explicit migration/version rejection rather than silent loss.
Keep the existing 53-test baseline until tests are deliberately updated to express
the revised contracts; a passing old suite alone does not verify the new product.

The next planned work is [Stage 1](stage-1-plan.md), not automatic continuation of
M5. Implementation has not started. First-slice priorities remain in
[refinement-roadmap.md](refinement-roadmap.md); exact Stage 1 contracts freeze at
G1, and later stages are detailed only after their predecessor closes. Hosted accounts/collaboration,
marketplace/commercial planning, general raster/temporal GIS, RAG infrastructure,
and elaborate branching remain outside the initial target.
